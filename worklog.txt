===============================================================================
1. WHAT HAS BEEN BUILT
===============================================================================

Set-up
- Created the project with the front end, back end and shared parts kept apart.
- Added automatic checks: code style, type checking, and a check that stops
  recordings, the prototype file or passwords being committed by accident.
- Added a guard that blocks anyone pushing straight to the main branch.
- Matched the database setup to the CRM's (same version, same style of
  settings, same way of applying database changes).

Training content
- Loaded everything from the approved prototype into the database and checked
  it word for word: 28 stages, 66 lessons, 231 quiz questions, 34 Status Guide
  entries, and the stage list for each of the 9 tracks.
- Re-running the load changes nothing, so it is safe to repeat.

Signing in
- Staff sign in with their CRM email and password, then a 6-digit code from an
  authenticator app on their phone.
- The academy never sees or stores the CRM password; it asks the CRM privately.
- A manager can disable someone, and they are thrown out within seconds.
- Too many failed attempts locks the account for a while.
- Every sign-in event is written to an audit trail that cannot be edited.
- IT has commands to reset a lost authenticator and to set someone's track.

The training itself
- Stages unlock one at a time. The server decides this every time, so nothing
  the browser sends can unlock a stage early.
- Quizzes are marked on the server. The answers are never sent to the browser
  before someone submits.
- Fail a quiz and you see which questions were wrong, but not the answers.
  Pass and the answers are shown. Retakes are unlimited and the best score is
  kept.
- Finishing a level or a department academy is recorded, and finishing Level 1
  queues the "ready to start work" message to their manager.

Recordings and video
- All 7 real recordings (6 calls and the FOS walkthrough video) are stored on
  the server itself, never in the code.
- They play through the app only, after checking the person is signed in and
  the stage is unlocked.
- The player has no skip bar, and the server checks a listen is genuine:
  claiming 7 minutes of listening in 8 seconds credits only the 8 seconds.
- Empty "coming soon" slots never block anyone.

Screens
- Sign-in, dashboard, stage, lesson reader, quiz and results, Status Guide
  search, certificates — all matching the approved prototype.
- The two interactive lessons (DSAR tabs, Status Guide search) work.

Manager dashboard
- Live list of everyone: who is online, their track, current stage, attempts,
  fails and best scores.
- A "needs attention" list: 3 fails on a stage, or 7 days with no activity.
- Disable, re-enable, assign a track, remove a track, per-person detail.
- Download everything as a spreadsheet file.
- Preview any track without recording anything.
- Staff cannot see or reach any of it. Every manager action is logged.

Certificates
- A proper PDF in the FAC colours when someone finishes a level or a
  department academy.
- Staff can download theirs; managers can download anyone's.
- A public page anyone can use to check a certificate is real. It shows only
  the name, programme, what was completed and the date.

Behind the scenes
- Background jobs run on Redis with retries, and anything that keeps failing
  is parked where someone can see it.
- Proved that killing the worker mid-job and restarting does the work exactly
  once, never twice.

Testing and safety
- 639 automated tests, plus 41 browser tests that walk the real journeys.
- A real backup and restore rehearsal: backed up the database AND the
  recordings, restored into a throw-away copy, and checked all 9 ways it
  could have gone wrong. All passed.
- Deployment files written: web server configuration, the two programs, and
  a deploy script.

Problems found and fixed today
- A real hole in the lesson-text cleaner: certain hidden tags let styling
  through onto the page. Nothing could reach it yet, but the protection we
  claimed we had did not exist. Replaced it properly and added a second layer.
- Personal data was leaking into log files (a certificate recipient's address,
  database errors echoing a staff email, and failed sign-ins storing whatever
  address was typed into a permanent table). All fixed.
- The quiz screen had the question sitting outside its box with a gap.
- The manager table made the whole page scroll sideways.
- Disable failed with an unhelpful message when a manager clicked it on their
  own row.
- There was no way to remove a track once assigned.
- Nine settings were compulsory but meant nothing; they are gone.

2. KEY DECISIONS MADE
===============================================================================

- New starters: the CRM account is created first, by IT, as today. Then they
  sign in to the academy with it. No separate academy sign-up.
- Only the CRM role "Management" makes someone a manager. IT can override
  individuals.
- A new starter waits for a manager to assign their track. (Setting it
  automatically from their CRM role is parked for later.)
- Mattermost is dropped. There is no approval chat flow, and the second CRM
  change is no longer needed.
- No AWS. Recordings, the video and certificate PDFs live on the company's own
  server, streamed by the app. There is no cloud storage and no public links.
- No email provider chosen yet, so nothing is sent. Every message is written
  and stored, ready to go out when a route is picked.
- The academy uses the same database as the CRM but in its own area, with a
  restricted login that has no access to any CRM data.
- Website address: academy.fastactionclaims.com (still to be confirmed).
- Everything stays switched off until Brad signs off in writing.
- Front end in React with Tailwind (plain JavaScript); back end in TypeScript;
  modern modules only.
- Work is committed locally and pushed in one batch when you say so.
